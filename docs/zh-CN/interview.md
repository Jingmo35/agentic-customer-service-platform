# 面试问答：从调用链理解，不逐行背诵

本文件是配套学习材料，基于仓库 `d2523b0` 的实现组织。回答中的“原项目”指上游设计，不代表你独立实现。代码链接用于核对，不能替代实际阅读与演示。

## 1. 这个项目和普通 RAG 聊天机器人有什么区别？

RAG 主要解决“怎样找到依据并回答问题”。本项目还要控制业务动作：客户可以查询订单、申请退款、取消订单或创建工单。对写操作，模型提出建议后，服务端还必须进行目标解析、参数和业务校验、策略判断、确认、再次校验以及幂等写入。知识依据不能代替执行权限。

**追问：**退款申请为什么不能直接根据政策文本执行？政策是否适用，还取决于当前客户、订单归属、订单状态和本次动作的确认状态。

## 2. 为什么使用 LangGraph？它替系统保证了什么？

工作流有多条分支和跨轮状态：问答、读工具、写操作、待确认、挂起恢复、拒绝与错误。图结构可以明确组织节点职责和条件路由，检查点支持恢复状态。业务授权仍需策略和数据库代码负责，不能说用了 LangGraph 就天然安全。

看 [graph.py](../../app/agent/graph.py) 的 `build_graph()`，分别找到问答分支、首次写操作分支和确认后执行分支。

## 3. 为什么不直接相信 LLM 的工具参数？

模型输出可能有幻觉、错误引用或受到恶意指令影响。默认 `semantic_decision_v3` 将模型输出限制为语义建议，服务端结合可信身份、客户范围和业务记录解析目标并编译决策，再进行类型和业务校验。模型不能通过自己生成的客户 ID、订单 ID 或“允许”标签获得权限。

看 [compile_decision.py](../../app/agent/nodes/compile_decision.py) 和 [validate_tool.py](../../app/agent/nodes/validate_tool.py)。历史 `direct_tool_v1` 是兼容路径，不要与默认契约混讲。

## 4. 用户确认为什么还不够？

确认需要绑定具体持久化动作与参数，不能将任意一句“我确认”应用到任意动作。确认还可能过期；等待期间订单状态或策略输入可能变化。所以确认后仍要检查身份、动作、参数和当前状态，再决定是否执行。这解决检查与使用之间发生变化的问题，也叫 TOCTOU。

看 [create_pending.py](../../app/agent/nodes/create_pending.py)、[check_pending.py](../../app/agent/nodes/check_pending.py) 和 [revalidate.py](../../app/agent/nodes/revalidate.py)。

## 5. 如何避免重复退款？

准确说法是避免重复创建受控业务结果，本项目退款工具创建的是退款申请。幂等层用租户、操作者、操作类型和幂等键查询回执，并比较请求指纹。匹配时返回原结果；同一键对应不同内容则拒绝。首次业务写入与回执在同一事务边界内处理，数据库约束用于应对并发冲突。

看 [idempotency.py](../../app/services/idempotency.py) 和 [refunds.py](../../app/tools/refunds.py)。幂等不能只靠前端禁用按钮，也不能把它概括成“所有网络故障都保证 exactly once”。

## 6. 工具超时为什么不能统一重试？

读操作和写操作的重试风险不同。写操作在超时时可能已经提交成功，如果结果未知又盲目重试，就可能产生重复副作用。原项目区分失败类型；提交连接失效等情况会标记未知写入结果，停止盲目回放。恢复应依赖可信业务状态和回执，而不是让模型猜执行结果。

看 [execute_tool.py](../../app/agent/nodes/execute_tool.py) 和 [commit_business_write](../../app/services/idempotency.py)。

## 7. Checkpoint、记忆和业务数据库有什么区别？

- Checkpoint 保存工作流状态，支持跨请求恢复。
- 记忆保存可用于后续理解的客户偏好或上下文，受策略与隐私约束。
- 业务数据库记录订单、退款申请和执行回执等真实业务结果。

记忆不能授予权限，检查点也不能替代业务事务。它们可以使用同一 PostgreSQL 服务，但语义和数据结构不同。

## 8. RAG 的主线是什么？为什么混合检索？

知识文件切分和索引后，问题进入稠密与词法检索，再合并、重排和校验依据。稠密检索通常补充语义匹配，词法检索适合明确词汇，两者互补。是否真有收益需要数据集和对照验证，不能仅因为使用混合检索就宣称准确率提高。

本地默认使用确定性 embedding，适合演示与测试，不能当成真实语义模型的效果证据。看 [hybrid.py](../../app/rag/retrieval/hybrid.py) 与 [deterministic.py](../../app/rag/embeddings/deterministic.py)。

## 9. 如何处理提示注入？能彻底解决吗？

原项目将模型建议与执行权限分开，并采用安全检查、可信客户范围、类型与业务校验、策略、确认和数据库约束等多层控制。检索与记忆中的文本都不能获得执行授权。这些边界能减少恶意指令造成的业务副作用，但不能因为有限测试通过就声称彻底消除所有提示注入风险。

## 10. 你怎么验证这个项目？

先说明自己实际做过什么：环境启动、健康检查、已有核心测试、前端构建与测试、具体演示。然后说明证据范围：Fake 模型与 SQLite 单元测试用于确定性逻辑；实际模型测试用于语义行为；PostgreSQL 等真实服务验证持久化与并发；上游报告不是个人测试结果。

**不要回答：**“仓库 README 写了大量测试，所以我验证了所有功能。”

## 11. 可观测性有什么价值？

它帮助区分请求、检索证据、模型建议、策略决定和工具结果，定位失败在哪一层。操作台展示的是受约束的投影，不是模型隐藏推理。Jaeger 是否真的收到 Trace，需要看实际运行证据，不能只看容器处于运行状态。

Docker Compose 的 backend 覆盖 `OTEL_ENABLED=true`，本地直接启动可能使用 `.env` 中的 `false`。追踪开启和 Trace 成功导出也不是同一件事。

## 三个反事实练习

1. **去掉确认后再次校验，会怎样？** 用户等待期间状态变化，旧参数和旧策略判断可能不再适用。
2. **只在内存中记录幂等键，会怎样？** 重启丢失、跨实例不共享、无法与业务写入原子关联。
3. **把知识库文本当成授权，会怎样？** 错误、过期或恶意文本可以越过身份与业务规则边界。

答题方法：先讲结论，再讲一个业务例子，最后指出代码位置。遇到尚未阅读的实现，明确说明学习范围，不即兴编造设计。
