**客服 Agent 平台｜开源复现与中文化**

- 基于 React/TypeScript 完成操作台显示层中文化，覆盖导航、交互提示、状态及证据说明；整理核心工程文档中文版和按调用链组织的学习资料。
- 运行仓库已有 Agent、RAG 和业务工具核心测试，98 项通过；项目提供知识问答、订单查询、退款申请、取消订单及人工升级等受控工作流。

使用条件：第二条需以中文化改动和前端验证结果为证据；第三条的 98 项是你此前提供的运行结果，不是你新增或设计了 98 项测试。若本次重新运行结果不同，以最新运行记录为准。

如果版面只有两条，把第一、三条合并为“完成本地部署及核心测试验证（98 项通过）”，保留第二条作为本次具体改动。

## 学完核心链路后可补充的写法

下面的表述需等到你完成学习路线中的第 2～5 步、能定位源码并讲解后再使用：

- 梳理“语义建议—目标解析—业务校验—策略判断—确认—再次校验—幂等写入”退款申请调用链，分析模型输出与后端执行权限的边界。
- 验证退款申请、业务校验失败和同一动作重复确认场景，记录确认状态、执行结果与审计证据。

不能仅看演示卡片就写第二条。应实际执行相应模式下的请求，保留会话/动作标识和数据库或操作台证据，并说明是否调用了真实模型。

## 贡献审计

| 表述 | 证据与边界 | 当前能否写 |
| --- | --- | --- |
| 本地复现与部署 | 已有 Docker Compose 环境及健康检查 | 可以 |
| 操作台中文化 | 本次前端显示层源码改动及检查结果 | 改动验证完成后可以 |
| 核心文档翻译与学习资料 | `docs/zh-CN` 中文文件 | 文档审校完成后可以 |
| 运行 98 项核心测试 | 你此前运行上游已有测试的结果 | 可以，不能写成新增测试 |
| 实现 LangGraph 工作流 | 上游已有实现；个人未独立开发 | 不这样写 |
| 设计幂等/安全/RAG 架构 | 上游已有实现 | 不这样写 |
| 深入理解确认与幂等 | 要能找到代码并解释设计取舍 | 学习验收后再写 |
| 提升准确率、降低延迟 | 没有个人基线与对照实验 | 不写 |
| 生产上线、真实客户接入 | 目前是本地工程参考实现 | 不写 |
| 支持中文客服能力 | 界面中文化不代表模型、检索和政策语料中文能力已验证 | 不写成已实现 |

## 90 秒项目介绍模板

> 我做的是一个基于开源参考实现的客服 Agent 复现与中文化项目。它除了知识问答，还支持订单查询、退款申请和人工升级等业务流程。核心设计是模型只提出语义建议，后端负责客户范围、业务状态、策略、确认和幂等执行。我完成了本地部署与核心测试验证，并将操作台和关键文档中文化。业务工作流和安全机制来自原仓库，我没有把它们当成独立设计成果。后续我重点沿退款申请调用链学习，理解为什么用户确认后仍要再次校验，以及重复操作如何避免重复业务写入。

最后一句仅在你完成相应学习后使用；尚未完成时改为“目前正在重点学习退款申请调用链”。

## 面试官问：你到底写了什么？

> 核心业务源码来自开源项目。我完成了环境复现、运行验证、前端显示层中文化，以及中文文档和学习资料整理。AI 协助了这些工作，我会对照改动与验证结果解释它们。对于核心业务架构，我可以讲我已学习的部分，不会说是自己从零设计。

中文化属于前端改动，不能包装成独立实现整个客服 Agent。AI 辅助不妨碍你展示成果，但你需要能解释修改范围、验证方式和技术边界。
